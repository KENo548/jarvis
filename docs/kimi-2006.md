# SAGE / JARVIS — Master Build Roadmap
### From Current State → Cognitive Operating System

> **Core Principle:** Your future advantage will not come from a superhuman custom LLM.  
> It will come from the orchestration ecosystem *around* the model.
>
> Sage does not become powerful primarily through model scale.  
> It becomes powerful through: **orchestration, memory coherence, observability, embodiment, retrieval quality, execution reliability, workflow continuity, operational learning.**
>
> Fine-tuning is an optimization layer added after the ecosystem becomes measurable and stable.  
> The immediate objective is therefore: **build a continuously improving cognitive operating system** — not merely "train a smarter model."

---

## The Correct Sequence (North Star)

```
1. Stabilize ecosystem
2. Instrument ecosystem
3. Measure ecosystem
4. Gather operational traces
5. Identify true bottlenecks
6. Fine-tune surgically
```

Premature fine-tuning is almost always an attempt to compensate for weak orchestration.  
Build the substrate first. Fine-tuning is the final optimization layer — not the foundation.

## PHASE 1 — Build The Observability Layer / Instrument Everything
**Goal: No blind spots. Every interaction is observable, measurable, replayable, and diagnosable.**

> Without observability: debugging becomes impossible, fine-tuning becomes blind, regressions become invisible, optimization becomes guesswork.  
> This phase is more important than fine-tuning.

### 1.1 — Unified Interaction Logging / Build The Logging Layer

This is not optional. Without this, every improvement is a guess.

**Minimum schema (store in SQLite at `jarvis/logs/interactions.db`, categorized by domain from day one):**

```json
{
  "interaction_id": "str",
  "session_id": "str",
  "workflow_id": "str",
  "timestamp": "str",
  "agent_name": "str",
  "model_name": "str",
  "input_text": "str",
  "assembled_context": "str",
  "retrieved_memories": [],
  "tool_calls": [],
  "tool_outputs": [],
  "reasoning_trace": "str",
  "output_text": "str",
  "latency_ms": 0,
  "token_usage": {},
  "auto_eval": {},
  "human_feedback": {},
  "correction": "str",
  "retry_count": 0,
  "was_edited": false,
  "was_abandoned": false,
  "followup_prompt": "str",
  "success_score": 0.0
}
```

**Python logging function:**
```python
def log_interaction(
    agent_name: str,
    input_text: str,
    output_text: str,
    model: str,
    duration_ms: int,
    session_id: str,
    task_id: str,
    memory_context_snapshot: dict,   # what context was injected
    tool_calls_made: list,           # which tools were invoked
    reasoning_trace: str,            # chain-of-thought if available
    quality: str = None,             # good / bad / mediocre
    correction: str = None           # what it SHOULD have done instead
):
```

**Critical fields most people skip:**
- `memory_context_snapshot` / `assembled_context` / `retrieved_memories` — what the agent knew at call time
- `tool_calls_made` / `tool_calls` — which tools were invoked during that run
- `correction` — the most important field for future fine-tuning; a binary good/bad flag is nearly useless alone
- `session_id` / `task_id` / `workflow_id` — links interactions into workflows, not just isolated calls
- `reasoning_trace` — chain-of-thought if available
- `was_edited`, `was_abandoned`, `followup_prompt` — behavioral signals

Store in SQLite initially. PostgreSQL later if needed.

### 1.2 — Capture User Behavioral Signals / Behavioral Signal Capture

Your behavior is the most honest signal in the system. The system must learn from your behavior.

| Signal | Meaning |
|---|---|
| You used the output directly / immediate reuse/copy | Implicit acceptance — strong positive signal / likely success |
| You edited the output / manual edits | The edit itself is a correction training example |
| You re-prompted / rapid re-prompting | The first response failed — log the follow-up / likely failure |
| You abandoned the task / abandonment | Silent failure — hardest to catch, very important / hidden failure |
| Repeated retries | Orchestration weakness |
| Approval override | Planner/routing issue |
| Ignored output | Low utility |

Most fine-tuning pipelines ignore behavioral signals entirely. Building this in from the start is a significant edge. These implicit signals are often more valuable than manual ratings.

### 1.3 — Capability Telemetry & Automatic Self-Evaluation

Track across all agents:
- Failures and error types
- Hallucinations (detected and logged)
- Retries and re-prompts
- Routing outcomes and overrides
- Tool errors and successes
- Approval overrides
- Workflow completions vs abandonments

This becomes your debugging layer, your benchmark layer, your training dataset, and your future reinforcement signal.

**After every major agent response, run a lightweight judge prompt** (even just another Ollama call) that scores:

| Dimension | Example |
|---|---|
| Task completion | Did it finish the request? |
| Format adherence | Schema correctness |
| Hallucination risk | Fabricated tools/memory |
| Tool validity | Valid calls |
| Reasoning quality | Coherent plan |
| Constraint following | Obeyed instructions |
| Safety | Avoided dangerous behavior |

This turns your logging from passive to active. Your dataset quality goes from "whatever I manually flagged" to "every single run, automatically graded." This creates continuously labeled operational data.

**You must be able to replay prior executions.** A replay suite captures the full state snapshot of each run:

```python
class ReplayScenario:
    input_text: str
    memory_context_snapshot: dict   # exact memory state at time of run
    tool_availability: list          # which tools were available
    prompt_version: str              # which prompt was active
    model_version: str               # which model was used
    orchestration_state: dict        # full orchestration context
    expected_output_criteria: list   # what a good response looks like
```

Store: prompts, context snapshots, memory state, routing decisions, tool availability, outputs.

Purpose: regression testing, orchestration debugging, benchmark comparisons, fine-tuning evaluation.

Start with **5 hand-written benchmark scenarios** — this takes a few hours and immediately gives you regression detection. Without replay testing, you will change a prompt, memory threshold, or routing rule and silently break something you fixed 3 weeks ago.

This is the agent-system equivalent of software unit tests. It is not optional at scale. Without replay: regressions become invisible, optimization becomes anecdotal.

### Completion Criteria
- Every agent call is logged with all fields above
- User behavioral signals are being captured
- Export script exists, produces valid JSONL on a dummy dataset
- All interactions are categorized by domain
- At least 5 benchmark replay scenarios written and running
- Auto-evaluation judge running on every agent call

## PHASE 2 — Retrieval & Memory Architecture / Memory Assembly Architecture
**Goal: Context coherence — your most likely future bottleneck / Make Sage contextually intelligent before attempting weight modification**

> Your future bottleneck is probably **context coherence**, not raw intelligence. Most advanced agent systems eventually become constrained by context pollution, not reasoning ability.
>
> This is likely the highest-leverage intelligence layer. A well-built RAG layer over your past interactions, project documentation, personal preferences, corrections, and codebase will likely outperform a fine-tuned model by a wide margin for a fraction of the compute cost — and it updates in real time without retraining.
>
> **Memory should arguably be your primary investment. Fine-tuning is the optional later enhancement.**
>
> The future bottleneck is likely: **context coherence** not: **model intelligence**.

| Memory Type | Purpose |

- Recency balancing
- Relevance scoring

## PHASE 5 — Meta-Observation & Continuous Learning
**Goal: The system improves itself continuously, not just when you review logs / Make the system capable of analyzing itself**

> This component is missing from most agent architectures and is a significant missed opportunity.
>
> As you collect telemetry, someone needs to be watching the patterns. Right now that's implicitly you, manually reviewing logs. A Meta-Observer automates this.

### 5.1 — Meta-Observer Agent

Create a lightweight observer agent.

**Responsibilities:**
- Analyze telemetry
- Detect recurring failures
- Identify unstable prompts
- Summarize retry patterns
- Detect routing weaknesses
- Identify hallucination hotspots
- Surface: which routing decisions are failing most, which prompts produce the most retries, which workflows are abandoned most often, which agents have the highest error rates
- Flag when replay benchmark scores regress

**What It Looks Like (Minimal Version):**
```python
def weekly_meta_observation():
    # Query logs for past 7 days
    # Identify top 5 failure patterns by frequency
    # Identify top 3 prompts with highest retry rate
    # Identify any replay scenario regressions
    # Output structured improvement recommendations
```

Even a simple weekly scheduled job that summarizes your logs and surfaces patterns is enormously valuable. This is low-cost to build and turns passive data collection into an active improvement loop. Even a weekly summarization prompt over logs is high leverage.

### 5.2 — Weekly Review Cadence / Ritual (30 Minutes)

Without a fixed cadence, log review never happens. Without cadence: telemetry becomes unused archive data.

Every week answer:
1. What were the 3 worst agent outputs / failures this week?
2. What pattern explains them? (prompt? memory? routing? model?)
3. What is the one targeted change to test this week?
4. What were the 3 worst failures?
5. What pattern caused them?
6. Which subsystem failed?
7. What single change should be tested next week?
8. Did performance improve or regress?
9. Run replay suite before and after the change — did it improve?

### Completion Criteria
- Meta-Observer running on a weekly schedule
- Outputs actionable, ranked improvement list each week
- Replay regression alerts firing when scores drop
- Weekly review ritual established

## PHASE 8 — Fine-Tuning (Surgical, Only After Stability)
**Goal: Surgical, high-leverage weight modification on a well-understood system / Apply surgical operational adaptation**

> By this point you have: real interaction data, labeled corrections, categorized domains, a working evaluation suite, replay benchmarks, and a clear picture of exactly what is failing and why. Fine-tuning is now targeted, not exploratory.

### 8.1 — What To Fine-Tune For / Fine-Tune ONLY For

✅ **Fine-tune for these:**

| Use Case | Valid |
|---|---|
| Tool-use precision and reliability | yes |
| Orchestration syntax discipline | yes |
| Structured output format consistency | yes |
| Routing decision alignment | yes |
| Your specific workflow conventions | yes |
| Approval logic patterns | yes |
| Memory formatting protocols | yes |
| Capability invocation syntax | yes |
| OS interaction patterns | yes |

### 8.2 — What NOT To Fine-Tune For / Do NOT Fine-Tune For

❌ **Do NOT fine-tune for these:**

| Use Case | Avoid |
|---|---|
| General intelligence or broad reasoning | avoid |
| Chat personality or tone / personality simulation | avoid |
| "Making the model smarter" / "AGI" behavior | avoid |
| Generic coding intelligence | avoid |
| Generalized reasoning scaling | avoid |

Small targeted LoRAs that make the model more operationally reliable and protocol-consistent work well. Trying to improve general reasoning through small LoRAs almost always disappoints.

### 8.3 — Use Lightweight Fine-Tuning

Preferred:
- LoRA
- QLoRA
- Small targeted adapters

Avoid:
- Full retraining
- Large behavioral overwrites

Maintain upgrade flexibility.

### 8.4 — The Fine-Tuning Process

**Step 1 — Dataset Preparation**
- Export categorized JSONL using your `export_training_data()` pipeline
- Filter to high-quality interactions (`quality = 'good'`)
- Prioritize examples that have human corrections
- Keep domain datasets separate (one dataset per agent type / capability domain)

**Step 2 — Lightweight Fine-Tuning**
- Use LoRA or QLoRA — not full retraining
- Target models: Llama 3.2 or Qwen2.5-Coder
- Run `python tools/finetune.py --train --domain coding` (domain-specific)

**Step 3 — Evaluate Before Deploying**
Every fine-tuned model must be benchmarked against:
- Previous model version (did things get better or worse?)
- All replay scenarios (regression detection)
- Routing accuracy benchmarks
- Hallucination rate comparison
- Memory consistency scores

Never deploy a fine-tuned model without running the full replay suite. Regressions are silent and common.

**Step 4 — Continuous Evaluation Loop**
```
fine-tune → replay benchmark → deploy if improved → collect new data → repeat
```

### Completion Criteria
- First fine-tune run on at least one domain-specific dataset
- Evaluated against full replay benchmark suite before deployment
- Performance improvement documented against baseline metrics
- Continuous evaluation loop established for future fine-tuning cycles
- Fine-tuning infrastructure ready
- Data collection active
- Ecosystem measurable

## The Biggest Risks To Watch For

**Risk 1: Fine-tuning before isolating bottleneck variables**  
If you fine-tune before completing Phase 3, the model will absorb architectural noise — you'll encode temporary workflow mistakes into weights and lose upgrade flexibility.

**Risk 2: Logging without corrections**  
A binary good/bad quality flag is nearly useless for training. What you need is: *what was wrong, and what should it have done instead.* The `correction` field is the most valuable field in your schema.

**Risk 3: No replay testing**  
Without replay scenarios, every change to prompts, memory thresholds, or routing logic is a guess. You will silently regress and not know why.

**Risk 4: Mixing datasets**  
Dumping all interactions into one flat training file prevents specialized LoRAs later and makes evaluation across domains impossible. Categorize from day one.

**Risk 5: Treating memory as secondary**  
For a personal agent system, context coherence is almost always the primary bottleneck — not model intelligence. A well-built memory layer will outperform a fine-tuned model in most real-world scenarios.
